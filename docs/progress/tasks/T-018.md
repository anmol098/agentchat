# T-018 — Isolate integration tests that inspect cluster-wide state

The migration runner's tests assert on advisory locks by counting rows in `pg_locks` against a fixed lock key. Both of those are cluster-wide, not database-scoped, so any other process holding the same lock on the same PostgreSQL instance is counted too.

That is not hypothetical here. Several agents run their suites against one shared development container at the same time, and the assertions fail intermittently as a result. The failure is indistinguishable from a real defect in the locking logic, which is the worst property a flaky test can have: it trains people to re-run rather than read.

It passes when the container is quiet and fails when it is busy, in both cases regardless of the code under test.

## Acceptance criteria

- [ ] The lock key is unique per test run rather than a fixed constant, or the test otherwise cannot observe another process's locks.
- [ ] Any assertion counting cluster-wide rows is scoped to this run's own key.
- [ ] The suite passes repeatedly while another suite runs concurrently against the same container. Demonstrate that rather than asserting it.
- [ ] The behaviour under test is unchanged: it must still prove that two concurrent migrators cannot both migrate, and that a failed migration releases its lock.

## Notes

Found by T-104 while finishing the token service, and correctly diagnosed rather than worked around: it verified the failure occurs with its own changes stashed and disappears when the container is idle.

Worth checking whether any other integration test makes the same assumption about shared state. A test that reads `pg_stat_activity`, a sequence, or a global setting has the same problem.
