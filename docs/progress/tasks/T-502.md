# T-502 — Migration runner with advisory lock and version guard

Safe automatic upgrades for self-hosters. Concurrent starts cannot race, and a rollback past a migration fails loudly instead of corrupting data.

## Acceptance criteria

- [ ] Migrations run on boot inside a Postgres advisory lock, so two starting instances cannot both migrate.
- [ ] `MIGRATE_ON_BOOT=false` disables the behaviour for operators who migrate as a separate step.
- [ ] The same logic is reachable through the image `migrate` subcommand.
- [ ] The server refuses to start when the database schema is newer than the binary knows, with a message naming the required version.
- [ ] Migration progress and duration are logged.
- [ ] Tests cover concurrent start, the disabled path, and the newer-database refusal.

## Notes

Plan section 12.2. The version guard turns a dangerous rollback into a clear error.

**Reprioritised.** This originally waited on the messaging schema, on the assumption the runner needed the full data model. It does not: it needs one migration to exist, which T-101 delivered. Meanwhile the container image refuses to boot without it, correctly, because migrations are bundled and it will not serve against a database it cannot verify. So this now blocks the deployment stack rather than trailing it.

T-501's Log carries the entrypoint contract: the runner must live at `server/src/migrate.ts` and compile to `dist/src/migrate.js`, exit non-zero on failure, handle SIGTERM, and take the migrations path explicitly because the Drizzle config is deliberately absent from the image. The node-postgres migrator is already in the production dependency tree; `drizzle-kit` is not, and must not be added to it.
