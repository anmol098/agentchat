# T-055 — Answer a too-fast device poll with the code that means it

`POST /auth/device/poll` absorbs a client polling faster than the interval it was given, and answers `CONFLICT`. That was the only code available: the frozen set had nothing meaning "you are going too fast". T-020 has now minted `RATE_LIMITED`.

Both sides say so in their own comments. `server/src/routes/auth.ts` explains that `CONFLICT` is used "because it is the only code left", and `packages/cli/src/commands/auth.ts` says the `CONFLICT` row in `POLL_SIGNAL_BY_CODE` "is a stand-in… when it lands, this adopts it by changing one key in that table, and nothing else in this file moves."

## Why it is its own task rather than part of T-020

The two halves must change **together**. The CLI reads `CONFLICT` as slow-down, so a server that starts sending `RATE_LIMITED` to an unchanged CLI strands a login: the client stops recognising the signal and either gives up or keeps polling at the rate it was asked to reduce. Minting a code is additive; changing which code a served endpoint returns is a wire-behaviour change, and it wanted its own review.

## Acceptance criteria

- [ ] The poll answers `RATE_LIMITED` when a client polls too fast, with `Retry-After` carrying the new interval exactly as it does today.
- [ ] The CLI adopts it. Check whether `CONFLICT` must keep working for one release so an older server and a newer client still interoperate, and say what you concluded — this is the compatibility promise in plan §12.4, and the answer is not obviously "no".
- [ ] `docs/protocol.md` §3.1 and §5 stop describing `CONFLICT`'s rate-limit use as a stand-in, and §13 drops the gap it records.
- [ ] `docs/cli.md` agrees.
- [ ] `pnpm protocol:check` is satisfied. Changing which code an endpoint returns is not a schema change, so expect it to report the contract unchanged — say so rather than treating silence as approval.
- [ ] A test that polls too fast and asserts the code, and a test that a login still completes through the whole flow.

## Notes

Raised by T-020, which minted the code and deliberately left this alone with the reasoning above. Read its Log.

Read `docs/protocol.md` §5 on the device flow first: `AUTH_PENDING` is the neighbouring signal, it is explicitly not an error, and how a client is meant to treat the two differently is the thing this must not blur.
