# T-064 — Publish the libraries under the `@stackgrid` scope

The first release attempt reached npm and was refused:

```text
npm error 404 Not Found - PUT https://registry.npmjs.org/@agentchat%2fprotocol
```

npm answers 404 rather than 403 for a scope a token cannot write to, so as not to reveal whether it exists. The `@agentchat` organization was not available. The maintainer chose `@stackgrid`.

Nothing was published: the refusal hit the first package, and dependencies go first precisely so a failure there leaves the registry untouched. The container image had already been pushed, which is the recoverable half by design.

## What changes, and what does not

- `@agentchat/protocol` → `@stackgrid/protocol`
- `@agentchat/client` → `@stackgrid/client`
- **`agentchat` stays `agentchat`.** The CLI is unscoped, the name is free, and it is what a user types: `npm i -g agentchat`. Moving it under a scope would change the install command for no benefit.

## Acceptance criteria

- [ ] Both manifests renamed, and every import across the workspace follows. `pnpm typecheck` is the check that proves none was missed.
- [ ] `release.yml`'s `PUBLISHED` list names the new scope. It is the list preflight uses to refuse a release whose packages depend on something unpublished, so a stale entry there is worse than a stale import.
- [ ] The packed tarballs carry concrete versions and install clean. Pack all three, install into an empty directory, run the binary.
- [ ] Documentation that names the packages is updated. Task files under `docs/progress/tasks/` are historical records — leave them.
- [ ] The licence boundary still holds: nothing under `packages/` imports from `server/`.

## Notes

The scope is the only thing moving. No version change, no wire change, no behaviour change — `pnpm protocol:check` should report the contract unchanged, and if it reports anything else something has been renamed that should not have been.

- So the CLI is `@anmol098/agentchat` and the command is still `agentchat`.
  `bin` names the command independently of the package, which is the whole
  reason a scoped package is not a worse experience here. The release workflow
  had conflated the two — it checked `bin[NPM_PACKAGE_NAME]` — and now carries
  both names separately.

- **The release moved to 0.2.0.** `@stackgrid/protocol@0.1.0` and
  `@stackgrid/client@0.1.0` are on the registry and immutable, and they carry an
  `UPGRADE_COMMAND` pointing at a package that will never exist. That artefact
  cannot be repaired, only superseded. A breaking protocol constant also moved
  `PROTOCOL_VERSION` to 5, and at 0.x a breaking change takes the minor.

- `MIN_CLIENT_VERSION` deliberately stays `0.1.0`. It is a floor, so leaving it
  low is permissive rather than wrong, and no CLI was ever published below it to
  be stranded by raising it.
