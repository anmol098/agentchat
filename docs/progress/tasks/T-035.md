# T-035 — One clock writes updated_at

The `updated_at` columns take their insert value from the database's clock and their update value from the application process's clock. Two different machines write the same column.

```
updatedAt: instant('updated_at').notNull().defaultNow().$onUpdate(() => new Date())
```

`defaultNow` is evaluated by Postgres. The update function is evaluated by Node. Measured against the development container just now, the two disagreed by 65 milliseconds, and the direction of the drift changes.

So `updated_at` can move backwards: a row updated after it was created can carry an earlier timestamp than its own creation, and two updates can land out of order. That is not hypothetical. It surfaced as a failing test asserting a rename bumps the timestamp, where the renamed row's value was four milliseconds behind the created row's.

In production the application and the database are on different hosts by design, so the drift is a deployment property rather than a container quirk. Anything that later reasons about this column, a synchronisation cursor, an audit trail, a cache validator, inherits the problem quietly.

## Acceptance criteria

- [ ] One clock writes the column, on both insert and update. Decide which and say why; the database's is the usual answer because it is the one both paths can reach, but the application's is defensible if it is used consistently.
- [ ] Every table with this pattern is fixed, not only the one that failed. There are at least two.
- [ ] A test proves the value never goes backwards across a create-then-update, and it must fail if the mixture is reintroduced.
- [ ] If the fix changes what the database writes, it needs a migration, and that migration must satisfy the compatibility rules.

## Notes

Found while verifying main, from a test that failed once and would have been easy to re-run and forget. The test was right and the schema was wrong.

Check whether `created_at` has the same issue anywhere, and whether any column mixes the two clocks in a less obvious way.

Note the session and message tables were written later and may already be consistent; confirm rather than assuming the problem is limited to the two tables named here.
