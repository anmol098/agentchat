# T-038 — Register the message routes and connect them to delivery

Two halves of one gap. The message and conversation routes exist and are not registered. The delivery service exists, is wired into the WebSocket handshake, and its fan-out method has no possible caller, because the message route options carry no delivery hook.

So today a message sent to a connected agent is persisted and never pushed. It arrives on that listener's next reconnect: durable and replayed, but a reconnect late, which is not what the product claims.

**This is deliberately one task, not two.** Registering the routes without the hook produces sends that persist and never push, which looks like it works until someone measures latency. The task that finished the WebSocket wiring identified this and declined to half-wire it for exactly that reason.

## Acceptance criteria

- [ ] Message and conversation routes registered, protected by omission like every other group.
- [ ] The send path calls delivery's fan-out **after** the message service returns. That ordering is what makes at-least-once delivery hold: the row is committed and visible on other connections before anything is pushed.
- [ ] A delivery failure never fails the send. The message is already durable; a socket that could not take it replays on reconnect.
- [ ] An integration test proving a message sent over HTTP reaches a connected socket without a reconnect. That single test is the product's headline claim, so it is worth writing carefully.
- [ ] The listener that was already connected receives it; one that connects afterwards gets it by replay. Both, in one test if that reads better.

## Notes

Read the Logs of the three tasks this depends on. The delivery task describes exactly what the send path should call and what to do when it reaches nobody; the wiring task describes the observer composition and the shutdown ordering.

This unblocks the listen command and the end-to-end suite, both of which are waiting on live fan-out rather than on anything in their own scope.
