# T-050 — A normal logout, retried, is answered with a security alarm

`rejectUnspendable` in `server/src/auth/tokens.ts` cannot tell a token revoked by logout from a token replayed after rotation. Both leave `revoked_at` set, so both get the reuse-detection answer:

> This refresh token has already been used. Every session for this account has been revoked as a precaution.

A client that logged out normally and then retried — a dropped connection, a re-run script, a user pressing the button twice — is told its account was compromised. That is alarming, wrong, and teaches people to ignore the message that matters.

The message is correct for an actual replay, which is why it is worded that way. The two cases are genuinely different and the column cannot currently express the difference.

## Acceptance criteria

- [x] A token revoked by logout is distinguishable from one revoked by reuse detection, in the data rather than by inference.
- [x] A retried logout gets a calm answer. `POST /auth/logout` is already idempotent and answers `200 {}`; this is about redeeming a logged-out token at `POST /auth/refresh`.
- [x] The reuse-detection alarm still fires, unchanged, for an actual replay. Prove both paths with tests.
- [x] **Do not make the answers distinguishable to an attacker who is guessing.** `docs/protocol.md` section 3.2 lists what is deliberately indistinguishable, and a caller holding a random string must not learn from the difference whether it was ever a real token. The distinction is for a caller holding a token it legitimately had; work out whether that is expressible and say so if it is not.
- [x] Any migration follows the expand/contract rules in plan section 12.3 and passes `./scripts/upgrade-test.sh all`.

## Design, worked out and blocked on one column

Written down here so that whoever is granted the paths does not have to redo the reasoning. Nothing below is implemented; this task changed no code.

### What the server actually does today

Verified against a running server on a throwaway database. Alice holds two live sessions. She logs out on the laptop and the client retries at `POST /auth/refresh`:

```text
POST /auth/logout  {laptop token}   → 200 {}
POST /auth/logout  {laptop token}   → 200 {}          (idempotent, as documented)
POST /auth/refresh {laptop token}   → 401 AUTH_REQUIRED
  "This refresh token has already been used. Every session for this account
   has been revoked as a precaution. Sign in again with: agentchat login"
```

The message is only half of it. `rejectUnspendable` reaches `revokeAllForUser` first, so **the desktop session — which did nothing — is revoked as well**, and the server logs `refresh token replayed; every live token for this account was revoked` with `revokedCount: 1`. The desktop client then refreshes, gets the same alarm, and produces a *second* false alert with `revokedCount: 0`, which contradicts `RefreshTokenReuseError`'s own documented invariant that the count is always at least one.

So the defect is not only alarming wording. A benign retry is a remotely reachable, self-inflicted sign-out of every session on the account, plus two false entries in the one log line that is supposed to mean credential theft.

### Why the distinction is expressible without leaking

The constraint from `docs/protocol.md` §3.2 is that a caller must not learn from the answer whether a string it holds was ever a real token. `POST /auth/refresh` has exactly two answer classes today:

- **G**, generic — `This refresh token is not valid. Sign in again with: agentchat login`. Unknown, or known and expired.
- **A**, alarm — the reuse message above. Known and revoked.

Class A is reachable only by presenting a preimage of a stored SHA-256 of 32 CSPRNG bytes. **A caller guessing strings cannot reach it at any budget**, so any split *inside* class A is invisible to a guesser: they see G, always, exactly as they do now.

That is what makes this task solvable, and it also fixes the shape of the answer. The calm answer must be **byte-identical to G**, produced by the existing `refreshTokenRejected()` builder. A new, gentler third message — "this session was logged out" — would give the answer set `{unknown → G, expired → G, logged out → L, replayed → A}`, and any holder of a harvested string would learn from `L` that the string was genuinely issued. That is precisely the leak §3.2 forbids, and it would be a *new* one. The distinction is therefore made by moving the logout case **into** the indistinguishable class, never by adding to it.

What remains distinguishable is what already is: a caller holding a genuinely issued, already-rotated token gets A. Its wording is deliberate and does not change, and reaching it costs the caller the whole chain.

### The residual trade, stated rather than buried

An attacker holding both halves of a stolen credential can call `POST /auth/logout` (it is authenticated) with the stolen refresh token, and the legitimate client's later refresh then gets G instead of A, with no chain revocation. Today it would get A. This is judged acceptable: that attacker already holds a live access token and a live refresh token, so the alarm arrives too late to prevent anything; and the alarm's own doctrine is that *two live copies exist*, which after a logout is false — the chain is terminal and nothing can be spent by anyone. The alternative is the status quo, where the alarm fires so often on benign retries that it trains people to ignore it.

The reason cannot be laundered: `revokeByHash` and `revokeAllForUser` both predicate on `revoked_at IS NULL`, so a row already revoked by rotation can never be relabelled by a later logout.

### The column, and why nothing else will do

`refresh_tokens` has no column that records *why* a row was revoked, and the existing columns cannot stand in for one:

- **Successor existence** — a rotation inserts its replacement with `created_at` equal to the predecessor's `revoked_at`. That is a perfect discriminator today and is exactly the inference the first acceptance criterion rules out; it breaks on a clock collision and on any future change to `mint`.
- **Overloading `expires_at`** (logout writes `expires_at = revoked_at`) needs no migration and is still wrong: `claimForRotation` tolerates `CLOCK_SKEW_TOLERANCE_SECONDS`, so a rotation up to a minute after expiry also produces `revoked_at > expires_at`, and a genuine replay would be handed the calm answer.
- **Deleting the row on logout** would work and needs no migration, but it destroys the audit record the schema comment promises to keep, makes a logged-out session indistinguishable from one that never existed *inside the server too*, and is a data-loss change to a table this task does not own.

So: one nullable column, `refresh_tokens.revoked_reason text`, written by whichever operation revokes the row.

```sql
ALTER TABLE "refresh_tokens" ADD COLUMN "revoked_reason" text;
ALTER TABLE "refresh_tokens" ADD CONSTRAINT "refresh_tokens_revoked_reason_valid"
  CHECK ("revoked_reason" IS NULL
      OR "revoked_reason" IN ('rotated', 'logout', 'reuse_detected')) NOT VALID;
ALTER TABLE "refresh_tokens" VALIDATE CONSTRAINT "refresh_tokens_revoked_reason_valid";
```

Expand-only, per plan §12.3, and it satisfies `scripts/lint-migrations.mjs`: a nullable `ADD COLUMN`, and the CHECK added `NOT VALID` then validated rather than taking a validating lock on boot. The pairing invariant `(revoked_at IS NULL) = (revoked_reason IS NULL)` **must not** be added here — release N-1 writes `revoked_at` without a reason and the constraint would reject its writes. It is a contract step for a later release, after a backfill.

Both rollback directions are safe, which is the point of the next paragraph. Rows revoked before the upgrade, and rows revoked by an older image running against the migrated schema, carry `NULL`. The read path must therefore treat **`NULL` as `rotated`** — today's behaviour, unchanged — so the upgrade changes nothing for existing rows and fails towards an alarm that might be spurious rather than towards a silenced one.

### The change in `server/src/auth/tokens.ts` (the path this task owns)

- A `RefreshTokenRevocationReason` union (`'rotated' | 'logout' | 'reuse_detected'`), exported, and `revokedReason` on `RefreshTokenRecord`.
- `claimForRotation` writes `'rotated'`, `revokeByHash` writes `'logout'`, `revokeAllForUser` writes `'reuse_detected'`, each in the same statement that sets `revoked_at`, so the reason cannot disagree with it.
- `rejectUnspendable` branches: `'logout'` → `refreshTokenRejected()`, the existing generic answer, revoking nothing and reporting nothing; `'rotated'` and `null` → the alarm and the chain revocation, exactly as now; `'reuse_detected'` → the alarm message, without a second cascade and without a second `onReuseDetected` event, since the account-wide revocation already happened and one incident should not produce one alert per surviving client.

### Tests

Both paths in `tokens.test.ts` over the in-memory store and in `tokens.integration.test.ts` against real PostgreSQL: a logged-out token redeemed at refresh gets the generic message, leaves every other live token of that account alone, and fires no reuse event; a rotated token replayed still revokes the chain, still fires the event, and still carries the alarm message word for word. Add a test that the generic message for a logged-out token is byte-identical to the one for a string that was never issued — that is the §3.2 property, and it is the one a later "helpful" reword would break.
