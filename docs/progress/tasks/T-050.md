# T-050 — A normal logout, retried, is answered with a security alarm

`rejectUnspendable` in `server/src/auth/tokens.ts` cannot tell a token revoked by logout from a token replayed after rotation. Both leave `revoked_at` set, so both get the reuse-detection answer:

> This refresh token has already been used. Every session for this account has been revoked as a precaution.

A client that logged out normally and then retried — a dropped connection, a re-run script, a user pressing the button twice — is told its account was compromised. That is alarming, wrong, and teaches people to ignore the message that matters.

The message is correct for an actual replay, which is why it is worded that way. The two cases are genuinely different and the column cannot currently express the difference.

## Acceptance criteria

- [ ] A token revoked by logout is distinguishable from one revoked by reuse detection, in the data rather than by inference.
- [ ] A retried logout gets a calm answer. `POST /auth/logout` is already idempotent and answers `200 {}`; this is about redeeming a logged-out token at `POST /auth/refresh`.
- [ ] The reuse-detection alarm still fires, unchanged, for an actual replay. Prove both paths with tests.
- [ ] **Do not make the answers distinguishable to an attacker who is guessing.** `docs/protocol.md` section 3.2 lists what is deliberately indistinguishable, and a caller holding a random string must not learn from the difference whether it was ever a real token. The distinction is for a caller holding a token it legitimately had; work out whether that is expressible and say so if it is not.
- [ ] Any migration follows the expand/contract rules in plan section 12.3 and passes `./scripts/upgrade-test.sh all`.
