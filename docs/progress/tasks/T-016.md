# T-016 — Reconcile the username grammar between the database and the protocol

Two definitions of a valid username disagree.

The database says `^[a-z0-9]+(-[a-z0-9]+)*$`: no leading, trailing, or consecutive hyphens. The protocol package says `^[a-z0-9][a-z0-9-]{0,38}$`: no leading hyphen, but trailing and consecutive hyphens pass.

So `alice-` and `alice--bob` are valid to every client and rejected by the database. Validation that passes at the boundary and fails at the storage layer turns a clean rejection into a constraint violation, which surfaces as a server fault rather than a message telling the user what is wrong.

Neither is harmful today, because these names come from GitHub logins and GitHub forbids both shapes. That is exactly why it will not be found by testing: it is latent until the identity provider changes, an account is created another way, or someone reuses the grammar for something else.

## Acceptance criteria

- [ ] One grammar, defined once, with the other side deriving from it or explicitly documented as a deliberate superset with a stated reason.
- [ ] Whichever direction is chosen, a name accepted by the protocol is accepted by the database.
- [ ] Tests cover the disputed shapes: trailing hyphen, consecutive hyphens, leading hyphen, and the length boundary.
- [ ] The protocol snapshot check is satisfied. Tightening a pattern is a breaking change under the additive-only rule, so if the protocol narrows, follow the acceptance process rather than working around it.
