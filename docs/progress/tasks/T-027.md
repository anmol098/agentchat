# T-027 — Reject an option given twice instead of silently taking the last

`agentchat status --project alpha --project beta` resolves to `beta` and says nothing. The argument parser documents a duplicate-option check, but it only fires for options declared as repeatable, and none are, so the check is dead for every option the CLI actually has.

Confirmed by running the built binary: the resolved project is `beta`, from source `flag`, with no warning on either stream.

The documentation already explains why this matters, and it is the right reason. A harness assembling a command line programmatically is exactly the caller that passes an option twice by accident, through a template applied over a default. Silently taking the last one means a message goes to the wrong project, and nothing in the output says so. This project exists to be driven by such harnesses.

## Acceptance criteria

- [ ] An option given twice is a usage error, exit 2, naming the option and both values.
- [ ] Genuinely repeatable options, if any are ever declared, still accept repetition.
- [ ] The behaviour holds for every option, not only ones declared repeatable, which is the gap today.
- [ ] A test drives the built binary with a duplicated option and asserts the exit code and the message.
- [ ] The parser's own documentation matches what it does. It currently claims a protection it does not provide.

## Notes

Found by T-209 while writing the status command, and reported rather than worked around.

Consider whether an environment variable and a flag disagreeing deserves the same treatment. That is arguably different, since precedence between sources is defined and deliberate, while the same source twice is a mistake.
