# T-023 — Register the milestone 1 routes on the application

The project, invite and agent route modules each export a register function and none of them is called. This task calls them.

It exists deliberately, created before those three tasks started rather than after. Twice already, several concurrent tasks each needed one line in a shared file none of them owned: the authentication wiring and the CLI package barrel. Each time every task correctly declined to cross the seam and the work sat finished but unreachable. The pattern is now predictable enough to schedule for.

## Acceptance criteria

- [ ] All three route modules are registered on the instance `createApp` returns.
- [ ] Every one of them is protected by omission. None is added to the public route set, because none of them should be public.
- [ ] An integration test proves each group is reachable with a valid token and refused without one. Reachable means a real request, not that the module was imported.
- [ ] No route module is edited. If one cannot be registered as written, that is a defect in that module and belongs in its task, not worked around here.

## Notes

Read the T-019 Log first: it explains how the application is split, how the public route set works, and why omitting a declaration fails closed.

Registration order matters only where a hook must see a route. T-019 verified the authentication guard is not order-sensitive; confirm that still holds rather than assuming it.

If this task is small enough to feel unnecessary, that is the point. Its predecessors were each one line too, and both went undone.
