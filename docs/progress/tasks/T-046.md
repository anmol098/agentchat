# T-046 — `docs/cli.md` describes the streamed message shape wrongly

The CLI reference says a `listen --json` `message` event and an `inbox` item match field for field. They do not.

A streamed message carries `recipientAgentId`, and carries **no `recipient` and no `parentMessageId`**. A listed message carries `recipient` and `parentMessageId`. A harness written from the reference — which is the audience this file exists for — breaks on the difference, and breaks at the point where it has already accepted the message.

The two shapes are built in different places and neither knows about the other: the frame in `server/src/routing/delivery.ts`, the listing in `server/src/routes/messages.ts`.

## Acceptance criteria

- [ ] `docs/cli.md` states both shapes accurately, and says plainly that they differ rather than implying they do not.
- [ ] It says which fields are absent from the streamed shape, not only which are present. A harness author needs the absence.
- [ ] Decide and record whether the difference is intended. If the two *should* agree, this task documents the truth and files the follow-up rather than changing the wire; changing a shape is a protocol change and belongs in its own task with a snapshot review.
- [ ] Cross-check every other claim `docs/cli.md` makes about a JSON shape against `docs/protocol.md` and the code while you are in there. One wrong claim of this kind usually has siblings.

## Notes

Found by T-314 while writing the end-to-end suite, which pins both halves with assertions now — so the shapes cannot drift further without a test failing, but the prose is still wrong until this lands.

`docs/protocol.md` is checked against the live schemas by `server/tests/protocol-doc.test.ts`. `docs/cli.md` has no such check, which is why this survived. Consider whether it should, and say what you concluded.
