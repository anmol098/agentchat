# T-044 — The migration runner's exit codes do not match its contract

The migration program documents an exit code per failure so an orchestrator can tell a retry from a dead end. At least one of them is wrong, verified by running it.

A database that is unreachable before the run starts exits **1**, not the documented **69**. The connection error surfaces as an aggregate error from the pool rather than wrapped, so the code that chooses an exit status never recognises it.

That matters to exactly the people the contract was written for: anyone writing retry logic against the documented table gets it wrong, and the reference stack only hides it because its migration container is ordered behind the database's health check. A self-hoster with a different arrangement, or a managed database that is briefly unavailable, sees a code meaning "misconfiguration, do not retry" for a condition that is purely transient.

Two agents found this independently while doing other work, which is a fair sign it is easy to hit.

## Acceptance criteria

- [ ] Every documented exit code is produced by the condition it names. Test each one by causing that condition, not by unit-testing the mapping function.
- [ ] An unreachable database exits with the retry code.
- [ ] Check the whole table rather than the one case named here. At least one other looked wrong under a quick probe: a missing migrations directory appeared to exit 0, which would mean a deployment silently proceeding with no schema applied. **Confirm or refute that first**, because if it is real it is worse than the exit code being wrong.
- [ ] The contract in the module, the plan, and the deployment guide all agree with the behaviour.

## Notes

Read the T-502 Log for why the codes are what they are, and the T-510 Log for how the mismatch was found.

If a documented code turns out to be unreachable in practice, say so rather than inventing a way to produce it. A contract listing codes nothing emits is worse than a shorter honest one.
