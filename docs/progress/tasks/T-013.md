# T-013 — Reconcile the health endpoint's error code with the protocol contract

`packages/protocol` holds a frozen set of error codes described as the contract that clients branch on. The health endpoint declares its own `DATABASE_UNAVAILABLE` outside that set, because the protocol package did not exist when the endpoint was written.

Two places that both describe themselves as authoritative for error codes is the confusion a frozen enum exists to prevent. Someone will eventually add a code to the wrong one.

The endpoint's own argument for staying separate is that it is operational rather than agent-facing: load balancers and operators read it, never a harness branching on machine-readable output. That may well be right. It has not been decided, only assumed.

## Acceptance criteria

- [ ] A decision is made and recorded in the implementation plan: either the code joins the frozen set, or the health endpoint is documented as deliberately outside the protocol with the boundary stated in one sentence.
- [ ] If it joins, the endpoint uses the shared code and the addition is noted as a minor, additive change per the compatibility rule.
- [ ] If it stays separate, no other operational endpoint is left to invent the same pattern independently; state where such codes belong.
- [ ] Existing tests still pass, and the response body shape is unchanged either way.

## Notes

Raised during review of T-007. Deliberately deferred rather than settled then, because T-201 was concurrently writing the full HTTP schema set and that work reveals whether the operational-versus-protocol split is a real boundary or a one-off.

This is a small change, but it is a contract decision, so it wants a deliberate answer rather than whichever way the next author happens to lean.
