# T-060 — Decide whether an agent may be called `agent-`

A user who types all three handles meets two different rules.

| Handle | `agent-` | `a--b` |
|---|---|---|
| Agent name | **accepted** | **accepted** |
| Project slug | rejected | rejected |
| Username | rejected | rejected |

**This is not a defect and there is nothing broken to fix.** Agent names have never had the boundary-versus-storage fault that slugs and usernames had: `agents_name_format` transcribes `AGENT_NAME_PATTERN` character for character, so the two sides agree exactly and nothing passes validation only to die at storage. Verified in T-059 against a live database, over 390 candidates, with zero disagreements.

It is a product question instead: what may an agent be called, and should the answer be the same shape a user already learned for their username and their projects?

## Why it needs deciding rather than leaving

`@alice/backend` is one string a person reads and types, and its two halves currently obey different grammars. `alice--bob` is not a username, but `alice/my--agent` is a valid address. Nobody has hit this, and it is the kind of thing that is obvious in hindsight the first time somebody does.

## What makes it expensive

Narrowing the agent-name grammar is a **third** break of the wire contract, after usernames (T-016) and slugs (T-025). The snapshot guard will refuse it until `PROTOCOL_VERSION` is raised again and a reason is recorded, which is the right friction but is not free. It also means a migration question for any existing agent names — of which there are none outside development today, and that will not be true after the first release.

**The window is now.** Before a tag this costs a version bump and a paragraph. After one it costs a rename path for real users.

## Acceptance criteria

- [ ] A decision, argued, not a preference. Either the three grammars converge, or agent names stay as they are and the plan says why the asymmetry is acceptable rather than merely tolerated.
- [ ] Weigh at least: one rule for a user to learn versus a third contract break; whether `-` at the end of a name is ever *wanted*; and whether the address grammar `@user/agent` should be stated once as a whole rather than as two halves that happen to compose.
- [ ] If narrowed: `PROTOCOL_VERSION` raised, the ledger entry written, `agents_name_format` moved with it, and the change verified against a live database by attempting real inserts — the method T-059 used, not by reading regexes.
- [ ] If not narrowed: D18's "left deliberately unsettled" paragraph is replaced by a decision with its reasoning, so the next reader is not invited to reopen it.
- [ ] `docs/protocol.md` agrees either way. It is currently correct for all three grammars.
