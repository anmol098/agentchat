# T-067 — The operator documentation reads like the build log, and the file names disagree about their own casing

The maintainer stood up the reference deployment on a fresh virtual machine from the published 0.2.0 artefacts, registered the GitHub OAuth application, connected from a CLI installed with npm, and exchanged messages with a second person on a second machine. The product worked. The documentation that got them there did not read as though it was written for them.

Three findings, all from that walk-through:

1. **The operator documents cite the project's internal papers.** `deploy/compose/README.md`, `docs/self-hosting.md`, `docs/upgrading.md` and `docs/cli.md` reference the implementation plan, the product requirements, decision numbers and task identifiers, none of which an operator has read or should need to. A self-hoster does not need to know that a timeout exists because of decision D6; they need to know the timeout and what happens if a proxy in front of them undercuts it.
2. **The section sign is everywhere and unexplained.** `section 12.5`, `section 4.3`, `section 3.2`. It is a legal and academic convention that most readers have to look up. Every cross-reference should say "section" and link.
3. **`deploy/compose/.env.example` pins `AGENTCHAT_VERSION=0.1.0`**, a release that was never published, and a self-hoster who copies it gets a version that cannot be pulled. T-068 adds the gate that keeps it at the release it ships with; this task moves it to 0.2.0.

And one that was visible without the walk-through: **the documentation files disagree about how they are named.** `implementation-plan.md`, `prd.md`, `upgrading.md` and `board.md` sit beside `cli.md`, `protocol.md` and `self-hosting.md`. One convention, written down, and every link updated.

## Acceptance criteria

- [x] The four named documents carry no reference to the implementation plan, the product requirements, a decision number, or a task identifier. Where the reasoning behind a choice matters to an operator, it is stated in the document itself, in the operator's terms.
- [x] No documentation file uses the section sign. Cross-references say "section N" and link where a link is possible.
- [x] `deploy/compose/.env.example` pins the current release.
- [x] Every Markdown file under `docs/`, `deploy/` and `examples/` is lower-case kebab-case. The exceptions are the files that GitHub and tooling find by name at the repository root (`README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `LICENSE*`), task files named by their identifier, and the two harness fragments named for the file they are merged into (`CLAUDE.agentchat.md`, `AGENTS.agentchat.md`). The rule is written in `CONTRIBUTING.md`.
- [x] Every link and path reference to a renamed file is updated, including the board renderer and the comments in configuration that cite a document by path. `node scripts/board.mjs check` passes and the rendered board links resolve.
- [x] `README.md` no longer says the project is unreleased, and its quick start matches what the 0.2.0 binary actually prints.
- [x] `docs/self-hosting.md`, `docs/upgrading.md` and `examples/README.md` no longer say `GET /version` is unserved. It has been served since T-041.
- [x] Every document touched reads as written for its audience: an operator, a CLI user, a harness author, or a contributor. The build history stays in `docs/progress/`.

## Notes

The internal documents (`docs/implementation-plan.md`, `docs/prd.md`, `docs/subagent-protocol.md`, everything under `docs/progress/`) keep their cross-references to each other; those are for contributors and the decision numbers are the point. They lose the section sign and gain the new file names, and nothing else.

`docs/protocol.md` is guarded by `server/tests/protocol-doc.test.ts`, which reads its endpoint headings and a handful of numbered sections. The headings do not change. Run the server unit tests after editing it.
