# T-051 — The reference client cannot name the close code the server now sends

T-048 added `CloseCode.BACKLOG_UNREAD = 4429`: the server closes a socket whose peer has stopped reading. `WsCloseCode` in `packages/client/src/websocket/frames.ts` duplicates the server's table and does not know it.

Nothing breaks. An unknown code falls through to `retry` by documented design, which is the right behaviour here. But the reference client cannot *name* what it received, so a consumer built on it sees a number where every other close gives it a case to match on — and `packages/` is MIT precisely so third parties build on it.

The duplication is the underlying issue. Two tables describe one wire vocabulary, and the licence boundary is why: `packages/` may not import from `server/`, so the client cannot simply use the server's enum.

## Acceptance criteria

- [x] `WsCloseCode` knows `4429` and names it the way the server does.
- [x] Its disposition is `retry`, matching what the fall-through already does, so no behaviour changes — only the ability to name it.
- [x] A test that fails if the two tables diverge again. If an honest one cannot be written across the licence boundary, say why, and say what the cheapest alternative is. — an honest one could be written; it goes through `docs/protocol.md` §9.6 rather than through the server, and all four of its assertions were made to fail before being trusted. See the Log.
- [x] `docs/protocol.md` section 9.6 is the shared source of truth; check the client against it rather than against the server's enum.

Directions are asymmetric on purpose: every documented row must be a member here under the same name, while the reverse allows 1001 and 1006 by naming them, not by a range check, so a private-use code minted on the client still fails. Each of the four assertions was made to fail before I trusted it - deleting the member, renaming it, adding a 4499 nobody documented, and making the section parse to nothing so the other three would have passed vacuously.
- 2026-09-09 — Cost of that test, stated rather than hidden: it reads a file and packages/client cannot. The package compiles with lib DOM and no Node types precisely so that reaching for fs is a compile error (Plan 5); node:fs under src/ fails typecheck with TS2591, confirmed rather than assumed. So it sits in packages/client/tests/, which the scope rule allows and Vitest and Biome already cover - and which tsc covers not at all, since tsconfig.test.json includes only src. Closing that hole needs rootDir '.' and the directory in include, which packages/cli already has, PLUS @types/node as a devDependency of packages/client, which it deliberately does not have. That last part is a decision somebody should take on purpose, not a chore, so I left it: the build project still excludes tests/ and would still reject node:fs under src, but it puts Node's types one tsconfig away from a package whose point is not having them. I compiled the test under exactly those settings to confirm turning them on is a no-op.
- 2026-09-09 — On whether a generated shared module is warranted: no - a shared one is, and the distinction matters. The licence boundary is not what forces this duplication. packages/protocol is MIT and both halves already depend on it; ErrorCode lives there and is shared, not transcribed twice. Close codes are duplicated only because they were never put there, and frames.ts already says the frame shapes 'should eventually live there' and do not yet because a milestone had not settled. A generator would add a build step, a checked-in artefact and a fresh failure mode (a stale generated file) to solve a problem an existing shared package solves with none of them. Moving the table into packages/protocol also buys something a generator would not: T-048 found that protocol:check reported the wire contract unchanged when it added 4429, because the snapshot covers packages/protocol and not the server's CloseCode. A close code that lived there would get additive-change enforcement it does not have today. The client keeps its own 1001 and 1006 on top, since those are RFC 6455 codes no server sends - a small honest split, not a reason against. The document check stays as the belt over it. This wants its own task: it touches server/src/websocket/frames.ts, packages/client/src/websocket/frames.ts, packages/protocol, scripts/protocol-snapshot.json and docs/protocol.md, which is five owners and a frozen-vocabulary decision, so it is not something one agent should widen a scope into.
