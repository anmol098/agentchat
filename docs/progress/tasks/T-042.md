# T-042 — Enforce the client version floor on the WebSocket handshake

The minimum-client-version guard runs as a request hook, and the socket upgrade is a raw listener, so no hook runs for it. A client below the floor is refused on HTTP and not on the socket.

This is a missing second line of defence rather than an open door: a listener must register its session over HTTP first, and that call is refused, so it never reaches the handshake. But the two paths disagree about a rule, and the one that disagrees is the one a self-hoster's users hit when something else changes.

The handshake already carries the client identifier in its first frame, so the information is there.

## Acceptance criteria

- [ ] A handshake from a client below the floor is refused, with a close code and reason a client can act on.
- [ ] The refusal names the same floor and the same remedy as the HTTP one. Two different messages for one rule is worse than one message in one place.
- [ ] An absent client identifier is still served, matching the HTTP behaviour: a third-party embedding the client library is not the command line tool and has no version to claim.
- [ ] A malformed identifier is refused rather than treated as absent, so an unparseable claim cannot buy passage.
- [ ] Tests for below-floor, absent, malformed, and current.

## Notes

Raised by T-503, which built the HTTP guard and could not file this itself.

The comparison function lives in the protocol package precisely because both sides need it and neither may import the other across the licence boundary. Use it rather than writing a second one; real version precedence is not string comparison, and getting it wrong locks people out of their own servers.
