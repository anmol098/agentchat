# T-059 — Decision D17 still states a slug grammar the project deliberately abandoned

`docs/IMPLEMENTATION-PLAN.md` D17 says:

> Project slugs use the same grammar as agent names, `^[a-z0-9][a-z0-9-]{0,31}$`.

Both halves of that are now false. `PROJECT_SLUG_PATTERN` is `^[a-z0-9](?:[a-z0-9]|-(?=[a-z0-9])){0,31}$`, and `primitives.test.ts` asserts that it **differs** from `AGENT_NAME_PATTERN` — the tie was broken on purpose, not by accident.

It was a considered change with the full acceptance path behind it: `PROTOCOL_VERSION` was raised to 3 and ten entries were written into the snapshot's breaking-change ledger, each carrying the reason. The old grammar accepted `payments-` and `pay--ments`, which `projects_slug_format` has always refused, so those slugs passed validation at the boundary and failed as a constraint violation at storage — reaching the user as a server fault. That is the same defect T-016 fixed for usernames.

**So there is no code defect here.** Verified against a live database rather than by reading regexes:

| slug | protocol | database | |
|---|---|---|---|
| `payments` | accepts | accepts | agree |
| `pay-ments` | accepts | accepts | agree |
| `payments-` | rejects | rejects | agree |
| `pay--ments` | rejects | rejects | agree |
| `-payments` | rejects | rejects | agree |
| 32 characters | accepts | accepts | agree |
| 33 characters | rejects | accepts | boundary stricter |
| 64 characters | rejects | accepts | boundary stricter |

Nothing is accepted at the boundary and refused by storage. The remaining disagreement runs the safe way.

The defect is that the plan still records the superseded decision, so anyone reasoning from it — as somebody just did, reporting this as a live bug — starts from a grammar the code abandoned.

## Acceptance criteria

- [x] D17 states what the project actually decided: that the slug grammar was narrowed to match storage, and that it is deliberately **not** the agent-name grammar. Keep the original reasoning visible rather than overwriting it; a decision record that hides having changed its mind is worse than one that is out of date.
- [x] The length asymmetry is written down: the protocol caps a slug at 32 characters and `projects_slug_format` at 64. That is the safe direction and needs no code change, but it is currently recorded nowhere and looks like an oversight to the next reader.
- [x] Line 97's `^[a-z0-9][a-z0-9-]{0,31}$` for **agent names** is still correct — `agents_name_format` matches it exactly. Do not change it while fixing the slug clause.
- [x] Say plainly that agent names therefore still admit `agent-` and `a--b`, which slugs and usernames do not. Whether that asymmetry should survive is a separate question; **do not settle it here**, but leave it visible so it can be.
