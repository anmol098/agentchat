# T-506 — Upgrade and rollback verification jobs

Automated proof that a self-hoster can upgrade without losing data and roll back without restoring a backup. This is the promise the project makes to anyone running their own server.

## Acceptance criteria

- [ ] A job starts the previous release, seeds data through its API, then starts the new build against the same database and asserts the data survived.
- [ ] A second job then runs the previous release against the migrated database and passes its smoke test, proving backward compatibility.
- [ ] A job verifies migrating across several versions at once, not just the adjacent one.
- [ ] A migration that breaks compatibility with the previous version fails the build.
- [ ] The jobs are skipped with a clear message before the first release exists.

## Notes

Plan §12.3, §12.6. This is what makes the compatibility rules real rather than aspirational.

**The rollback job must set `AGENTCHAT_ALLOW_SCHEMA_AHEAD=true`.** Running the previous release against a migrated database is precisely what the version guard refuses, so without that variable the job fails with exit 65 every time and the failure looks like a compatibility break rather than a missing flag. Raised by T-502; read its Log.
