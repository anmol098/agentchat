# T-036 — Share the client and project-lookup helpers across the commands

Building the API client is now written out privately in four command files. Turning a project slug into an identifier is written out in three. Each author saw the duplication and each correctly declined to fix it, because collapsing them means editing files other in-flight tasks owned.

This project has already run that experiment once. The server URL resolution reached three private copies before being unified, and two of them had silently drifted on whitespace handling before anyone noticed. The same drift is available here: four constructions of the same client can disagree about the version header, about which credential store they use, or about whether a warning sink is wired, and nothing would fail.

## Acceptance criteria

- [ ] One helper builds the client, used by every command that talks to a server. The private copies are deleted, not aliased.
- [ ] One helper resolves a project reference to an identifier and its membership. One author noted the shape the shared version wants: the whole membership row rather than just the identifier, because callers need the role.
- [ ] The credential store's warning sink is wired in the shared helper. Getting that wrong silently discards a security warning, which is exactly the kind of thing four copies get inconsistently right.
- [ ] Behaviour unchanged, proven by the existing command tests rather than new ones.
- [ ] A test that would fail if a fifth private copy appeared, if you can find an honest way to write one.

## Notes

Raised by T-402, which counted the copies. Read the T-026 Log for how the same problem was resolved for the server URL, including that the drift it prevented had already happened.

Schedule this when no other command task is in flight, since it necessarily touches several command files at once. That is a scheduling constraint rather than a reason to defer it: the copies multiply while it waits.
