# T-032 — Bound what an unread socket can buffer

Delivery hands bytes to the socket and returns, so a peer that has stopped reading never delays anyone else. It also never stops accumulating. Frames queue in that socket's buffer at up to a megabyte each, with no ceiling, until the process runs out of memory and takes every healthy connection with it.

That makes a single stalled listener an availability problem for everyone on the instance, not a latency problem for itself. A listener stops reading for ordinary reasons: a suspended laptop, a paused debugger, a harness that stopped consuming its own subprocess output.

The registry currently warns past a threshold and does not act, which was the right amount to do without a policy decision. This task is that decision.

## Acceptance criteria

- [x] A socket buffering past a documented limit is closed, with a close code that tells the client what happened.
- [x] Closing it is safe, and the reason is written down: the inbox is agent-scoped and unacknowledged messages replay on the next handshake, so a dropped socket loses nothing. Make sure that is still true when you close mid-delivery.
- [x] The limit is derived from something, not picked. Say what a reasonable listener's peak buffer looks like and how much headroom the number leaves.
- [x] A test proves a stalled consumer is disconnected before memory grows without bound, and that a healthy consumer on the same instance is unaffected.
- [x] Whatever the limit is, an operator can see when it fires.

## Notes

Raised by T-307, which measured the behaviour and deliberately stopped short of deciding the policy.

Consider whether the answer belongs on the socket or in the router. T-307's view is the socket, because the router should not need to know about transport buffering, and that seems right, but it is worth confirming once delivery exists.
