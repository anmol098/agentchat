# T-029 — Give process-spawning tests a timeout that survives a busy machine

Two unit tests fail on a loaded machine and pass on an idle one, with no assertion failure. Both time out at the five-second default: the exit-code contract test, which spawns the built binary once per error code, and the pending-authorization bound test, which fills a store to its limit.

Observed at a load average of 29 while several agents ran builds and suites concurrently. Continuous integration passes because each job gets an idle runner.

The failure is indistinguishable from a real defect: a timeout reports as a red test with no explanation, so the reader's first assumption is that the code broke. That is the same trap as the shared-database flake in T-018, one layer up, and it will find contributors building on a laptop that is also doing something else.

## Acceptance criteria

- [ ] Tests that spawn processes get a timeout proportionate to what they do, rather than the default meant for pure functions.
- [ ] The unit suite passes on a machine under heavy load. Reproduce the load rather than asserting it, for example by running several builds concurrently.
- [ ] A genuinely hung test still fails in reasonable time. Raising every timeout to a minute would trade one bad failure mode for a slower one.
- [ ] Whatever you change is explained where the next person will look, so nobody lowers it back on the grounds that the tests are fast on their machine.

## Notes

Found while reviewing other work, not by a failing gate, because the gate passes on an idle runner.

Consider whether the answer is a per-project timeout, a per-file override, or fewer spawned processes. The exit-code test spawns one binary per code; a single spawn asserting several codes might be both faster and clearer, and that would be a better fix than a larger number.
