# T-049 — The upgrade check's readiness probe races the image's initialisation server

T-506's verification script waited for PostgreSQL with `pg_isready` over the container's Unix socket. That can answer "ready" for the wrong server.

The official image initialises a cluster by starting a **temporary** server, running the init scripts against it, and shutting it down before starting the real one. The temporary server listens on the socket and deliberately not on TCP. So a socket probe can succeed against a server that is about to stop, and the next command finds the socket gone:

```
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: No such file or directory
```

Which is exactly how it failed. The script passed on its own pull request and on a developer's machine, where the image was already warm and initialisation had happened on some previous run, and then failed on the first CI job that pulled the image cold — on somebody else's branch, where the failure looked like their change had broken the upgrade promise.

## What was done

Readiness is now a real `SELECT 1` over TCP inside the container, and the `sql` helper connects over TCP too. Both halves matter: TCP cannot be answered by the initialisation server, and a query rather than `pg_isready` because PostgreSQL listens several seconds before it will answer one.

Verified by running `./scripts/upgrade-test.sh all` and then by CI, which reproduces the cold-image condition that a local run does not.

## Notes

Fixed directly on `main` by the orchestrator rather than delegated: it was a live gate reporting a false failure against an unrelated pull request, and every branch open at the time inherited it.

The general lesson is worth keeping. A test that passes locally and fails in CI is usually reported as CI being flaky. Here CI was right and the local run was the misleading one, because the local machine had state — a warm image — that CI never has.
