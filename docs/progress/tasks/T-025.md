# T-025 — Reconcile the project slug grammar with the database

The same defect T-016 fixed for usernames exists for project slugs, and it has now been confirmed twice.

The protocol accepts `^[a-z0-9][a-z0-9-]{0,31}$`; the database check requires `^[a-z0-9]+(-[a-z0-9]+)*$` with a longer cap. So `a--b` and `payments-` pass every client check and are refused by storage. T-107 works around it by validating the narrower grammar in its service and answering a clean rejection, which is right but leaves the contract still claiming those slugs are valid.

Two length caps also disagree: the protocol allows 32 characters, the database 64.

## Acceptance criteria

- [ ] One grammar, with the protocol matching what the database will actually accept.
- [ ] The length caps agree, or the difference is deliberate and documented.
- [ ] T-107's service-level workaround is removed or reduced to whatever remains genuinely necessary, so there is one place a slug is judged.
- [ ] Tests cover the disputed shapes: trailing hyphen, consecutive hyphens, leading hyphen, and both length boundaries.
- [ ] The protocol snapshot guard is satisfied through its acceptance path, not around it.

## Notes

Predicted by T-016 while fixing the username grammar, then hit for real by T-107. Read the T-016 Log: it went through the snapshot acceptance path first and reported what that felt like, including that a stale build makes the check report untruths.

There is a complication T-016 flagged and deliberately did not resolve: the slug pattern is currently tied to the agent-name pattern, with a test asserting they are equal, and the agent-name grammar does match its own database constraint. Decide whether they should stay coupled rather than assuming either answer.
