# T-057 — The version floor on the socket path binds nobody

T-042 added the floor to the WebSocket upgrade and it works. Verified against a running server: an upgrade carrying `X-AgentChat-Client: agentchat/0.0.1` is refused `426 UPGRADE_REQUIRED` with a message naming the floor and the command to run, and a current version falls through to `401` as before.

**But today's CLI never sends that header on the upgrade.** `packages/client/src/websocket/listener.ts` sends `{ authorization }` and nothing else. The version reaches the server only in the `hello` frame, where it is logged and not enforced. So the guard is correct, tested, and binds no client this project ships.

## The choice, and why one side of it is much cheaper

T-042 named two ways to close it and they are not equivalent.

**Send the header on the upgrade.** One line. An upgrade *is* an HTTP request, and `docs/protocol.md` §2.2 already says the CLI sends this header on every one, so this makes the client match its own specification rather than extending anything. No new wire vocabulary. This is the recommendation.

**Enforce on `hello` instead.** Post-handshake, so a refusal has to be a close code, which means minting one in the frozen vocabulary — and then `WsCloseCode` and `FATAL_CLOSE_CODES` in `packages/client` too, or a too-old client reconnects forever, because an unrecognised close code is transient by design. That is T-048's follow-up appearing in a new place, and it is a lot of surface to buy something the header already gives.

Take the first unless you find it is wrong, and say why if you do.

## Also here, because it is one line in the same area

`refuseUpgrade` in `server/src/app.ts` is called with the `WWW-Authenticate` challenge unconditionally, so the new `426` and the malformed-header `400` both carry `www-authenticate: Bearer`. Confirmed against a running server. Nothing in the repository reads it and no client is misled, but it reads as an authentication failure under `curl`, which is the opposite of what those two answers mean.

## Acceptance criteria

- [ ] A CLI below the floor is actually refused at the upgrade. Prove it with the shipped binary against a running server, not with a hand-made request.
- [ ] A current CLI is unaffected, and the header it sends matches what §2.2 says it sends.
- [ ] `426` and `400` from the upgrade path no longer carry `WWW-Authenticate`; `401` still does.
- [ ] The reference client's behaviour on a refused upgrade is unchanged — T-054 fixed a hang there, so check the refusal still settles rather than leaving a listener waiting.
