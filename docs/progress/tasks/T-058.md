# T-058 — The startup log invites the reader to conclude a working route is broken

The server logs an allowlist of five unauthenticated routes and then confirms only three of them. The two it never mentions again — `/healthz` and `/version` — both work.

```text
{"routes":["/healthz","/version","/auth/device/start","/auth/device/poll","/auth/refresh"],"msg":"routes declared as unauthenticated"}
{"method":"POST","url":"/auth/device/start","msg":"route registered without authentication"}
{"method":"POST","url":"/auth/device/poll","msg":"route registered without authentication"}
{"method":"POST","url":"/auth/refresh","msg":"route registered without authentication"}
```

Read in order, that says: five routes are meant to be open, three of them are. A reader concludes the other two are unregistered or sitting behind the guard. That is a reasonable conclusion and it is wrong.

## Why the two are missing

`registerAuth` installs the `onRoute` hook that emits the second line, so the hook can only ever see routes registered *after* it. `registerHealthRoutes` runs at `server/src/app.ts:567` and `registerVersionRoutes` at `:961`; `registerAuth` is at `:967`. Both are deliberately earlier — `docs/progress/tasks/T-041.md` explains that the version guard must run before authentication so a client below the floor is told *upgrade* rather than *unauthenticated*.

So the ordering is correct and the log is the defect. It reports on a set it cannot see all of, without saying so.

## This has already cost somebody an afternoon

It was reported as a live production bug: `GET /version` returning `401`, with this log as the evidence. Reproduced from the image and confirmed:

- **Current `main`, image built and run:** `GET /version` → `200`, body `{"version":"0.1.0","protocolVersion":3,"minClientVersion":"0.1.0"}`. `/healthz` → `200`. Both missing from the log all the same.
- **An image built from the commit before T-041:** `GET /version` → `401 AUTH_REQUIRED`, exactly as reported. That is where the original observation came from.

The endpoint was fixed hours before the report. The log will keep producing this misdiagnosis for every self-hoster who reads it.

## Acceptance criteria

- [ ] The log cannot be read as a claim that a declared route is missing. Either report every declared route's actual state, or say plainly that the per-route lines cover only routes registered after the guard.
- [ ] Prefer reporting the truth over softening the wording. A line that named `/healthz` and `/version` as *registered before the guard, and therefore open by construction* would answer the question the reader is asking.
- [ ] If a route is declared unauthenticated and genuinely never registered, that must still be visible. Today it looks identical to the healthy case, which is the part that makes this worth fixing rather than rewording.
- [ ] A test that fails if a declared public route stops being served. `server/tests/protocol-doc.test.ts` already enumerates the assembled application's routes and is the obvious place to compare against `PUBLIC_ROUTES`.

## Notes

Do not change the registration order. It is load-bearing: T-041 and T-042 both depend on the version routes and their guard preceding authentication, and T-042's `426` refusal on the WebSocket upgrade is decided in that window.

Read `server/src/plugins/auth.ts` around the `onRoute` hook, and `docs/progress/tasks/T-041.md` for why the order is what it is.

The reproduction, if it is wanted again: build the image, run it against a fresh database, and compare `docker logs` with `curl -i /version`. Note that an image older than the database's schema refuses to start with exit 65 rather than misbehaving, which is the schema-ahead guard working and was confirmed incidentally while investigating this.
