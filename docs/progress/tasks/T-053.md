# T-053 — A backlog above the socket ceiling can never be replayed

**A listener with a large enough backlog is permanently stuck, and no amount of reconnecting frees it.**

The numbers do not fit each other:

| Constant | Value |
|----------|-------|
| `REPLAY_PAGE_SIZE` | 100 messages |
| `MAX_MESSAGE_CONTENT_BYTES` | 1 MiB |
| `MAX_BUFFERED_BYTES` | 16 MiB (8 × `MAX_FRAME_BYTES`) |

One replay page is written into the socket before the next page is read, so a page can be up to **100 MiB against a 16 MiB ceiling**. Seventeen ordinary 1 MiB messages are enough to reproduce it.

The loop that results:

1. The listener connects and says `hello`.
2. Replay begins. The buffer passes 16 MiB partway through the first page.
3. The socket is closed with `4429` **before the handshake reaches `ready`**.
4. Nothing was acknowledged, so the backlog is exactly as large as it was.
5. The client retries with backoff, and the backoff grows toward its cap. Forever.

Reproduced by T-509 against the real server: closed at 16,784,112 buffered bytes. Committed there as an `it.fails` test, so the day it is fixed that test starts failing and must be un-marked.

This contradicts `docs/protocol.md` §9.8 and T-032's own acceptance criterion. T-032 was right that nothing is *lost* — the messages are all still there — but unreachable is not much better than lost, and it is worse than lost in one respect: the listener never stops trying.

## Acceptance criteria

- [ ] A listener with any legal backlog eventually reaches `ready`, however large the messages. Prove it with the seventeen-message reproduction, and un-mark T-509's `it.fails`.
- [ ] The fix is chosen by argument, not by moving a constant until the test passes. At least three candidates deserve consideration and rejection in writing: paging replay by *bytes* rather than by count; awaiting the drain between pages so the ceiling is never approached; and raising the ceiling, which only moves the threshold and does not remove it.
- [ ] The back-pressure ceiling still does what T-032 built it for: a peer that has genuinely stopped reading is still closed, and the process is still protected.
- [ ] `docs/protocol.md` §9.8 says what actually happens now.
- [ ] The distinction stays legible to an operator: a socket closed for not reading and a socket closed mid-replay are different events even if they share a close code.

## Notes

Found by T-509's chaos suite, which is exactly what it was written for. Read its Log for the reproduction and the exact byte count.

Read T-032's Log first for the derivation of the 16 MiB ceiling — it reasoned from a *pessimistic* 64 KiB per message and got ~6.5 MiB for a page, which is where the mismatch entered: the pessimistic case it chose was not the legal maximum. That is the kind of mistake worth understanding rather than just correcting.

## Log

- **It does not reproduce on an idle machine, and that is important for whoever
  fixes it.** T-509 committed the reproduction as `it.fails`. It failed on every
  local run — a developer machine with nine agents on it — and then *passed* on
  CI, which turned the green build red, because `it.fails` asserts a defect
  always manifests.

  Whether the ceiling is reached depends on how fast the peer drains relative to
  how fast the replay writes. Under load the writer outruns the reader and the
  buffer passes 16 MiB; on an idle runner it does not.

  The test is now skipped rather than deleted, with the reproduction preserved
  in place. Un-skip it as part of this task.

- That changes the shape of the fix. "Raise the ceiling" is now clearly the
  wrong answer, because the threshold is not the variable — the absence of
  back-pressure between the writer and the reader is. A replay that waits for
  the socket to drain before continuing cannot reach any ceiling, on any
  machine, at any load. Consider that first.
