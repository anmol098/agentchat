# T-039 — The protocol snapshot check does not know which way a shape travels

The compatibility guard treats every schema the same, but requests and responses break in opposite directions.

Adding a required field to a **request** is breaking: an old client sends a body without it and is refused. Adding a required field to a **response** is not: an old client receives a field it ignores. The guard reports both as breaking, so it demanded a major version bump for a response field that could not break anyone.

That was worked around by making the field optional, which is defensible on its own terms since a client may be talking to an older server. But the workaround and the correct answer happened to coincide, and next time they may not: the guard's advice will be to weaken a contract for a compatibility reason that does not apply.

The reverse gap is worse. Removing a field from a **response** is breaking and removing one from a **request** usually is not, so a guard that cannot tell them apart is lenient in exactly the direction that matters.

## Acceptance criteria

- [ ] The snapshot records which direction each schema travels, and the comparison applies the right rule to each.
- [ ] A required field added to a response is compatible; to a request, breaking.
- [ ] A field removed from a response is breaking; from a request, judged deliberately and documented either way.
- [ ] Existing accepted breaking changes in the ledger stay accepted; do not invalidate history to fix the rule.
- [ ] Self-test cases for each of the four combinations, following the precedent that a green run means the checker was capable of failing.

## Notes

Found by T-014 while adding an identifier to a response and being told it needed a major bump.

The direction is knowable: the schemas are named by convention, request shapes and response shapes are distinguishable, and the endpoint groups are explicit. Prefer deriving it over a hand-maintained list, which would drift.
