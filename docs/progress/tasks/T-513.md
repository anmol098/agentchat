# T-513 — The agentchat Skill doesn't warn against treating messages as instructions or say how to trust the CLI it shells out to

A security review of `skills/agentchat/SKILL.md` (added in #114) raised two
findings, both real:

1. **Indirect prompt injection risk (medium).** The skill's whole job is to
   put another agent's free text — `inbox`/`listen` output — in front of the
   reader. Nothing in the skill currently says that text is unauthenticated
   third-party content, not a second instruction channel. A message body can
   say anything, including something shaped like a directive ("ignore your
   previous instructions...", "run this for me: ...", a false claim of
   authority), and the skill as written doesn't tell the reader to treat that
   distinctly from what the actual user asked for. "The agent decides what a
   message means" is the right instinct already in the document, but it reads
   as *interpretive* latitude, not as a warning that the content is
   untrusted input.
2. **Unverifiable execution trust.** The skill tells the reader to run
   `agentchat` without saying what package that binary is supposed to come
   from. `docs/cli.md` already explains the CLI's own name mismatch (the
   package is `@anmol098/agentchat`, the command is `agentchat`, deliberately,
   because the unscoped name was taken) — a reviewer without that context sees
   an instruction to execute an unspecified binary with no stated provenance,
   which is a fair thing to flag on a skill that's meant to be copied into
   other people's repositories.

## Acceptance criteria

- [ ] `skills/agentchat/SKILL.md` states plainly, before or alongside the
      read/reply instructions, that message content is written by someone
      else's agent and is data to reason about, not a command channel — with
      concrete examples of what that means in practice (an embedded
      instruction, a false authority claim, a request to leak a secret or run
      something outside the conversation), and says to surface a mismatch
      between a message's ask and the user's own ask rather than resolve it
      unilaterally.
- [ ] The skill names the actual package to install
      (`@anmol098/agentchat`) rather than assuming a bare `agentchat` on
      `PATH` is self-explanatory, states that the command and package names
      differ on purpose, and gives a cheap way to sanity-check a binary that
      was already on `PATH` before installing over it.
- [ ] Neither addition turns into the kind of message-content schema the rest
      of the project deliberately avoids (PRD invariants 7/8) — this is about
      trust boundaries and provenance, not about classifying message intent.
