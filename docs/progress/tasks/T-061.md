# T-061 — The release pipeline accepts a pre-release tag the rest of the project cannot serve

`release.yml` handles pre-releases deliberately and well: `vX.Y.Z-rc.1` is parsed, the image takes its exact version only, `:latest` does not move, and npm gets the `next` dist-tag instead of `latest`. Somebody thought about it.

Nothing else in the project did. Attempting `0.1.0-rc.1` runs into three separate walls, each of which is a considered decision rather than an oversight:

1. **`MIN_CLIENT_VERSION` must be a bare `X.Y.Z`.** Its test says why: *"The CLI prints it verbatim in 'Server requires agentchat >= X.Y.Z', and compares against it, so it must parse as semver with no range operator, no `v` prefix, and no pre-release suffix."*
2. **`CLI_VERSION` carries the same assertion.**
3. **A pre-release sorts below the release it precedes**, which is correct semver and exactly the problem. Measured against this repository's own comparator:
   ```text
   0.1.0-rc.1  vs  0.1.0  ->  -1 (below)
   ```
   So with the floor at `0.1.0`, a `0.1.0-rc.1` CLI is refused by its own server with `UPGRADE_REQUIRED` and told to install the version it already is. Lowering the floor to `0.1.0-rc.1` fixes that and breaks the two assertions above.
4. **`UPGRADE_COMMAND` is hardcoded to `npm i -g agentchat@latest`.** A pre-release publishes to `next`, so a refused user is told to install something that does not exist yet.

So the release machinery can cut a release candidate that the product cannot actually run.

## Acceptance criteria

- [ ] Decide whether this project ships pre-releases at all. **A defensible answer is no** — then the workflow's pre-release handling should refuse the tag with a message saying so, rather than building an artefact nobody can use. Do not assume the answer is yes because the workflow implies it.
- [ ] If yes: the floor, the two version constants and the upgrade instruction all have to understand a pre-release. In particular `UPGRADE_COMMAND` cannot be one constant string — a user below a pre-release floor needs `@next`, and one below a stable floor needs `@latest`.
- [ ] If yes: the two "bare semantic version" assertions are relaxed deliberately, with their original reasoning answered rather than deleted. They are right about what they are protecting; something has to protect it differently.
- [ ] Either way, `release.yml` and the version constants stop disagreeing about what a version may look like.

## Notes

Found while preparing the first release. The maintainer chose a release candidate specifically to reserve the npm names without freezing the wire contract, and the attempt was abandoned rather than pushed through by editing the assertions to match — which is what filing this is instead of.

The comparator already handles pre-release ordering correctly (`comparePrerelease` in `packages/protocol/src/version.ts`), so the arithmetic is not the problem. The problem is everything that assumes a version is three numbers.

If the answer is that pre-releases are not worth supporting, say so in `docs/implementation-plan.md` section 12.1 where the versioning rules live, so the workflow's pre-release branch reads as vestigial rather than as a promise.
