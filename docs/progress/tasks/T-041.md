# T-041 — Wire the heartbeat and the version endpoint

Two finished modules with no caller, and one small service addition they need. Created as its own task because this is the fifth time on this project that finished work has sat unreachable behind a shared file nobody owned.

## What is missing

- **The heartbeat.** It needs constructing, adding to the observer composition beside delivery, attaching to each socket as it is accepted, and stopping at shutdown. Its own Log names all four.
- **The version endpoint.** One registration line, and it must go **before** authentication is registered, so a client below the floor sees the upgrade refusal rather than an authentication error. Both answers are true; only one tells the caller what to do.
- **A mark-stale path on the session service.** The heartbeat needs it and declared the interface rather than reaching into a file it did not own. The contract it asked for: move an active or stale session to stale and update its last-seen time, leave an ended session alone **without throwing**, and scope it to the caller like every other session mutation.

That last point is easy to get wrong. A socket closing after the session was already ended is the correct shutdown order for the listen command, so treating it as a conflict would make every clean exit log a failure.

## Acceptance criteria

- [ ] The heartbeat runs: a silent socket is closed and its session marked stale, and a responsive one is not.
- [ ] The version endpoint answers unauthenticated, and a client below the floor is refused with the upgrade message rather than an authentication error.
- [ ] The mark-stale path added to the session service with the contract above, including that an ended session is not an error.
- [ ] Timers stopped at shutdown; the process still exits promptly.
- [ ] An integration test covering the silent-socket path end to end, rather than only the module in isolation.

## Notes

Read the Logs of both tasks. The heartbeat explains why it is one sweep rather than a timer per socket, and why its failure to mark a session stale is safe: the existing sweeper catches it within the minute regardless, so this is a latency improvement on a guarantee that already holds.

Once the version endpoint is wired, two workarounds can go: the release smoke test asserting a container label instead of the endpoint, and the status command reporting the server as unreachable.

- **Held at review: wiring the heartbeat as written breaks reconnection, and
  the branch must not merge until that is fixed.** Three separately-correct
  modules contradict each other the moment they are connected:

  1. The heartbeat marks a session `stale` whenever its socket closes — cleanly
     or not. That is T-309's stated design, and on its own it is right:
     presence should stop claiming a listener that is not connected.
  2. The handshake refuses any session that is not `active`, closing with
     `4403`. That is `docs/protocol.md` section 9.2, and on its own it is right.
  3. The reference client treats `4403` as **fatal** and stops its retry loop,
     because "only registering a new one can fix it, and that is the caller's
     decision, not a decision a retry loop is allowed to make on its own". And
     `agentchat listen` registers a session exactly once.

  Together: the first disconnect ends the listener permanently. That is the
  precise failure this product exists to prevent.

  Reproduced against the assembled server, with a fresh session:

  ```text
  after-create       status active
  first hello        {"type":"ready","pending":0}
  (clean close)
  after-close        status stale
  reconnect hello    {"type":"error","code":"SESSION_INVALID"}
  ```

  Confirmed as a regression by A/B: the same fixture leaves the session
  `active` on `main` and `stale` on this branch.

- The fix belongs here rather than in a follow-up, because shipping the wiring
  without it ships the regression, and shipping neither leaves the heartbeat
  unreachable — which is the whole reason this task exists.

  **The proposed resolution is that `hello` revives a `stale` session to
  `active`.** `stale` means "nothing is connected right now", and a `hello` is
  exactly the evidence that something is connected again. It is consistent with
  section 10.4, which says only a session that has been *swept* — that is,
  `ended` — cannot be revived. It keeps the heartbeat's presence semantics
  honest and makes step 2 of section 10.4 ("if the session is still active,
  hello with the same sessionId") true again rather than nearly-always false.

  `server/src/websocket/handler.ts` is added to `paths` for that one condition.
  No active task owns it; T-042 declares it and has not started.

- Whoever finishes this must also update `docs/protocol.md` sections 9.2 and
  10.4, which currently describe the refusing behaviour, and add a regression
  test for the connect/close/reconnect sequence above.
