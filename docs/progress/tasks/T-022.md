# T-022 — Stop the migration job requiring credentials it never uses

Running migrations now fails unless `JWT_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are all set. A database migration has no use for any of them.

The migration entry point loads the whole server configuration, which was a deliberate choice: it makes the job fail for the same reasons as the server it precedes, so a misconfiguration surfaces before traffic arrives rather than after. That reasoning was sound when the configuration held little beyond a database URL. Adding authentication turned it into a requirement that an operator supply OAuth credentials to run a schema change.

The cost is concrete. The rollback verification job in the release pipeline runs migrations in isolation. An operator applying migrations as a separate step before switching traffic must now hand a migration container the login secrets. And a self-hoster who has not yet registered an OAuth app cannot migrate at all, which is the wrong order to force.

## Acceptance criteria

- [ ] Migrations run with only the configuration they use, at minimum the database URL and the migration settings.
- [ ] The intent behind the original choice is preserved: a misconfigured server must still fail before serving traffic, not after. Say how you kept that.
- [ ] The boot path, where the server migrates and then serves, still validates everything, since there the full configuration genuinely is required.
- [ ] A test proves migrations succeed with no authentication variables set.
- [ ] Whatever you split, the failure messages stay as good as they are now. They currently name each variable and how to obtain one.
