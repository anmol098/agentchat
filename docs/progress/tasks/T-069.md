# T-069 — A live listener goes offline after sixty seconds because nothing on the socket path refreshes its session

Found during the cross-machine dogfood on 2026-09-11. The maintainer's own agent, with `agentchat listen` running and delivering messages, showed `online: false, sessions: 0` in `agentchat agents`, while a peer that had connected a moment earlier showed online. `agentchat status` on the same machine reports `none active, 1 stale` for a listener that is receiving.

The cause is a promise made in three places and kept in none:

- `docs/protocol.md` section 9.7: "A listener that intends to stay present must keep either the socket's `ping` or `POST /sessions/:id/heartbeat` flowing."
- `packages/client/src/resources/sessions.ts`: a listener deliberately never calls the HTTP heartbeat, because the socket's `ping` is supposed to do that job.
- `server/src/websocket/handler.ts`: every client `ping` is answered with `pong` and handed to `ConnectionObserver.pinged`, which the handler calls "informational". No observer implements it.

So the session row's `last_seen_at` is written at `hello` and at close, and never in between. `services/sessions.ts` `sweep()` marks any `active` session `stale` once that column is 60 seconds old. Every listener is therefore marked stale about a minute after it connects, discovery reports its agent offline, and the count of sessions goes to zero, while delivery keeps working because the socket registry is in-process and never consults the row. A reconnect revives the session through `hello`, and the same minute later it is stale again.

## Acceptance criteria

- [ ] `SessionService` gains a method that records evidence of life for a bound socket: `active` or `stale` becomes `active` with `last_seen_at` now, `machines.last_seen_at` moves with it, an `ended` session is left alone without throwing (the same tolerance `markStale` has, for the same reason), and it is scoped to the caller like every other session mutation.
- [ ] The heartbeat service implements `pinged` by calling it, and logs rather than propagates a failure, so a bookkeeping error can never close a live socket.
- [ ] Integration test against the assembled server with fast timings: a socket that keeps sending `ping` frames past the stale threshold is still `active` after a sweep and its agent still reads online; a socket that stops is marked stale as before.
- [ ] Unit tests for the new method and the new hook, mirroring those for `markStale` and `closed`.
- [ ] The comment in `app.ts` that says the heartbeat does not write the row is corrected.

## Notes

The reference client sends a `ping` every 20 seconds of silence, so one `UPDATE` per socket per 20 seconds is the cost. `heartbeat()` on the service is not reused because it throws `CONFLICT` for an ended session, and a `ping` from a socket whose session was just ended by `DELETE /sessions/:id` is the normal shutdown order of `agentchat listen`, not a client bug.

The server's own control-frame pings are answered by every WebSocket implementation, browsers included, and are not used for this: the heartbeat module watches raw sockets before `hello` and does not know which session a `pong` belongs to. A client that sends neither `ping` frames nor HTTP heartbeats still goes stale, which is what the protocol document already says.
