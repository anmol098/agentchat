# T-040 — Disclose the invite identifier, and let it be revoked

**The original framing of this task was wrong and has been rewritten.** It said inviting somebody could not be done from the terminal. It can: T-207 shipped `agentchat project invite`, which mints a code and prints it, and `docs/cli.md` documents it. Confirmed against the built binary.

What is actually missing is narrower and more awkward:

- **The mint output withholds the identifier.** `projectInviteView` emits `{ code, expiresAt, project }`. `docs/protocol.md` §6 says the create response is the only place an invite identifier is ever disclosed, and there is deliberately no endpoint turning a code back into one. So an identifier that is not printed is an identifier nobody can ever hold.
- **Revocation therefore has no reachable argument.** The server route, the service and `RevokeInviteResponseSchema` all exist. `packages/client/src/resources/projects.ts` has `createInvite` and no `revokeInvite`, so nothing in the client reaches `DELETE /projects/:id/invites/:inviteId` either.

The two halves are not separable. A revoke command shipped alone would take an argument no user could obtain.

## Decisions already made, so this is mechanical

Argued in the escalation and recorded here rather than left to be re-decided.

- **It goes under `project`, not a new top-level group.** Both routes are `/projects/:id/invites…`, so every subcommand of a standalone group would carry `--project`; the code-addressed half is already `project join`; and a second top-level way to mint would leave the *documented* one as the one that withholds the identifier.
- **`project invite` stays a leaf.** Promoting it to a group (`project invite create|revoke`) would break the shipped `agentchat project invite` invocation. That is a public CLI surface change and needs plan-level agreement, not a subagent's judgement. Revocation lands as a sibling leaf, `project revoke-invite <inv_…>`, implemented in `invite.ts` and composed into the group by a small change in `project.ts`.
- **Revoke takes the identifier positionally and never the code.** That is what keeps a live bearer credential out of shell history, `ps` output and proxy logs. No `--code` convenience flag: it would need the lookup endpoint that deliberately does not exist, and minting one is a disclosure decision that belongs in the plan.
- **The identifier is not a credential and must appear in both renderings of create.** A `--json` consumer that cannot see it cannot revoke.
- **Proposed shapes.** Create becomes `{"id":"inv_…","code":"…","expiresAt":"…","project":{"id":"prj_…","slug":"…"}}` — additive, so no existing consumer breaks. Revoke returns `{"invite":{"id":"inv_…"},"project":{"id":"prj_…","slug":"…"},"revoked":true}`, matching the `{…, "joined": true}` convention `projectJoinedView` set. Revoke echoes no code back.

## Acceptance criteria

- [ ] `packages/client/src/resources/projects.ts` gains `revokeInvite`, reaching the endpoint that already exists.
- [ ] `agentchat project invite` prints the identifier as well as the code, in both the human and `--json` renderings, and says the identifier is disclosed once.
- [ ] `agentchat project revoke-invite <inv_…>` revokes by identifier, with `--json`.
- [ ] The mint output keeps saying plainly that the code is a bearer credential: anyone holding it can join until it expires or is revoked.
- [ ] The client is built with `clientFor` from `packages/cli/src/client.ts`. T-036 collapsed five private constructions into that helper and added a guard that fails if a sixth appears.
- [ ] Tests against a stubbed server for both commands, including that revoking an already-revoked invite behaves as T-014 decided.
- [ ] `docs/cli.md` updated in the same pull request, per protocol §7.6.
