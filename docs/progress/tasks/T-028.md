# T-028 — Session diagnostics endpoint

The plan lists a session listing endpoint and describes it explicitly as diagnostics for the status command. No task owns it, no protocol schema defines it, and no client method calls it.

The status command works around the gap by deriving a session count from the project agent listing, whose rows already carry presence and an exact count. That is correct as far as it goes, and it cannot report what someone with a stuck listener actually needs: which machine, which runtime, which working directory, how old the session is, and its identifier.

That is the whole point of the endpoint. An agent that is not receiving messages is the failure this product will be debugged for most often, and right now the tool can say only that a count is zero.

## Acceptance criteria

- [x] The listing endpoint from plan section 3, returning per-session detail rather than a count.
- [x] Its request and response schemas live in the protocol package. T-302's pull request lists nine schemas it wrote locally and expected to move there; check whether this is among them before writing new ones.
- [x] A caller sees only sessions belonging to agents they may see. Read T-106's disclosure reasoning first: a session listing that leaks another user's machine names is worse than one that leaks an identifier.
- [x] The status command uses it and reports per-session detail, replacing the derived count.
- [x] Integration tests cover the visible and not-visible cases.
