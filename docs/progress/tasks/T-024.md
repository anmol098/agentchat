# T-024 — One implementation of the user config directory

Two modules each compute where the user's configuration lives, from the same environment variables, by separate code. The credential store has `configDirectory`; the configuration module has `userConfigDir`.

They agree today only because a review caught them disagreeing. One honoured a relative value for the config-home variable and the other ignored it, as the specification requires. With such a value set, tokens would have been written under the home directory while the user configuration went somewhere relative to the working directory, and the same tool would have looked in two places without saying so.

That was fixed by making the second match the first. This task removes the reason it can happen again. Duplication that must stay in agreement is a bug waiting for the next person who changes only one copy, and nothing in the build would catch it.

## Acceptance criteria

- [ ] One function computes the directory. Both modules use it.
- [ ] Which module owns it is decided deliberately: the credential store depends on the configuration module or the reverse, but not a cycle, and not a third module created only to hold one function unless that is genuinely the cleanest answer.
- [ ] The behaviour is unchanged, including that a relative value is ignored and an empty one falls back.
- [ ] A test covers the disputed cases directly: unset, absolute, relative, empty.
- [ ] The package barrel still exports the composed paths rather than the ingredient, which is what T-021 deliberately chose.

## Notes

Raised independently by T-021 while curating the package surface, having reached the same conclusion as the T-205 review: publishing both implementations would have published the duplication.

Small, and worth doing before more modules need the same path.
