# T-070 — A frame received before a close is dropped if a slow hook was still running when the close arrived

Found while fixing T-069. The socket handler chains every received frame onto one promise so that frames are handled strictly in order, which is right: an `ack` must not overtake the `hello` before it. But `disconnected()` is not on that chain. It sets `open = false` at once, and `handle()` begins with `if (!open) return`, so any frame that was received before the close and was still waiting its turn behind a hook that had not finished is silently discarded when its turn comes.

The first version of T-069 made this visible: `pinged` awaited a database write, and the wiring suite's round trip, which sends `ping`, then `ack`, then closes, lost the `ack` every time. T-069 sidestepped it by running the touch beside the queue instead of on it. The hazard remains for the hooks that legitimately await the database: `bound` (replay) and `acked` (the inbox write). A listener that sends two acknowledgements and closes, or that closes while its replay is still being written, loses whatever was queued behind the awaited hook. The loss is a replay, not corruption, because delivery is at-least-once, but a client that did everything right is made to pay for it, and `agentchat listen` closes on SIGTERM immediately after its last acknowledgement.

## Acceptance criteria

- [ ] A close is handled after every frame received before it. Chaining `disconnected()` onto the same promise the frames use is the obvious shape; if a different one is chosen, say why.
- [ ] A frame that arrives after the close is still refused, and hooks that need the socket (a `bound` that would replay into a socket that is gone) still see it as closed.
- [ ] An integration test in the wiring suite: two `ack` frames followed at once by a close, both acknowledgements land.

## Notes

`handle()`'s `open` guard exists so that a frame arriving during teardown does not start a replay into a dead socket; that purpose stays. What changes is only where the close sits in the order.
