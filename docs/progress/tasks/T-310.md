# T-310 — Client WebSocket transport with reconnect

The listening half of the client: a durable connection that survives network failures, server restarts, and token expiry without losing messages.

## Acceptance criteria

- [ ] Reconnect uses exponential backoff with jitter from one second to a thirty-second cap.
- [ ] Every reconnect re-sends hello so the server replays anything pending.
- [ ] An expired access token is refreshed and the connection retried, without prompting the user.
- [ ] Messages are deduplicated by identifier so a replay after a lost acknowledgement is invisible to the consumer.
- [ ] Connection state changes are surfaced to the caller as events rather than printed.
- [ ] Tests against a mock server cover reconnect, replay, deduplication, and refresh mid-connection.

## Notes

Plan §4.4, §5. Deduplication here is what makes at-least-once delivery tolerable for consumers.
